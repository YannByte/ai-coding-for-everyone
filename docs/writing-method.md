# 本书的写作方法

本书借鉴 ASD-STE100 的受控语言原则：让读者用较少的猜测理解作者的意思。这个方法用于全书的论述、案例、操作、练习和翻译，也用于配套文档。写作的目标是帮助读者作出判断，并做出适合自己的工作工具。

## 参考依据与本书的取舍

ASD-STE100 面向英文技术文档，由写作规则和受控词典组成。词义明确、术语稳定，是它减少歧义的重要方法。参见 [官方说明](https://www.asd-ste100.org/about_STE.html) 与 [官方 FAQ](https://www.asd-ste100.org/STE_faq.html)。

本书参考 [Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf) 的程序性写作规则：指令直接表达动作；必要条件先于动作；顺序动作分别交代；不能把读者必须执行的动作藏在附注里。

以下是本书根据读者和案例制定的写作约定，不是标准条文的翻译。中文不套用英语词典、词性或词数限制；英文版本也不因采用这些约定就宣称完全符合 ASD-STE100。中文表达与排版另见 [中文写作规则](chinese-writing.md)。

执行顺序、工作状态和证据记录见 [写作工程流程](production.md)。已确认的项目决定继续生效，不从空白提示词重新规划。

## 按任务使用

这些规则适用于正文、案例、练习和翻译。开始前读取 [项目定位](project.md)、[全书脉络](../book/zh-CN/README.md) 和目标目录的 AGENTS.md。

| 任务 | 执行范围 |
| --- | --- |
| 起草 | 按本文件准备并完成正文，标明证据和试做缺口 |
| 改写 | 修改用户指定范围，保留事实、逻辑、限制与确定程度 |
| 校对 | 只处理指定的错字、标点或术语，不自行重排整章 |
| 审稿 | 按 [审稿规则](review.md) 记录问题；仅审阅时不修改正文 |
| 翻译 | 同时执行 [翻译规则](../translations/AGENTS.md)，记录原文版本与审阅状态 |

起草或改写后，使用审稿规则检查交付内容。规则不预设章节数、篇幅或固定叙事模板。

## 写作前：先说明读者要解决什么

每章起草前，写清以下五项。可以放在章节草稿的写作说明中，正式正文不必照抄这些标签。

| 项目 | 写清什么 |
| --- | --- |
| 工作问题 | 读者手里有什么材料，原来怎样做，具体卡在哪里 |
| 本章判断 | 读完后，读者应该能作出哪一个判断 |
| 本章结果 | 读者能完成什么，怎样看出是否完成；概念章可以是明确范围或判断标准 |
| 必要知识 | 读者已经知道什么，还需要在本章解释什么 |
| 证据与缺口 | 哪些来自真实来源，哪些是教学设定，哪些还没有试做 |

一个章节可以包含多个环节，但应共同支持本章判断。不能只用功能清单、提示词数量或代码长度说明章节价值。

## 论述：让读者看见判断怎样产生

从具体工作进入问题，再说明可选做法、选择理由和适用条件。案例结果要能支持本章判断；结果尚未验证时，保留设计状态。

每段围绕一个主要意思展开。需要连接原因、条件或转折时，写出关系。不要为了缩短句子删掉「如果」「因为」「但」后面的必要说明。可以用长短不同的句子，也可以直接称呼读者为「你」。

用读者熟悉的对象解释概念。例如，先说明「替换本月的 Excel 文件后，汇报中的哪些数字需要变化」，再引出输入文件和输出文件。术语首次出现时说明用途；后文采用 [术语表](terminology.md) 的同一表达。

使用明确的执行者和动词。「让 AI 编写读取表格的程序」与「程序读取表格」描述不同环节，不能都写成「AI 处理数据」。把「优化一下」「智能整理」「处理完成」改成读者能够观察或判断的内容。

案例中的重复工作、判断困难和失败过程可以保留叙述。比喻可以帮助理解，但要交代它与实际机制的边界。自然语气与准确表达同时保留。

## 操作：让读者知道下一步做什么

只在确实需要读者动手时使用步骤。按实际执行顺序组织，写清以下内容：

1. 交代开始前需要的文件、工具状态和条件。涉及覆盖、删除或上传时，在动作前说明对象与后果。
2. 每个步骤给出一个主要动作。写明对象；有多个相似对象时，用名称区分。
3. 区分读者的操作、AI 的回复和程序的行为。程序自动完成的事不写成读者要执行的指令。
4. 在需要判断是否继续的位置，说明预期结果和核对办法。
5. 结果不符时，说明先停止什么、保留什么，以及依据哪些现象继续检查。

条件、操作和结果必须有来源或试做依据。缺失内容标记为待试做，不能为了补全步骤编造按钮、路径、耗时或恢复方法。发布练习前，应补齐这些缺口。

## 提示词与对话：说明表达需要的方法

展示提示词时，交代当时已有的文件、读者的目标和不能改变的要求。随后解释提示词中的哪些信息影响了结果。读者应能替换自己的材料和规则，而不只是照抄一段话。

AI 回复只作为当次回复的记录。代码、文件和实际结果需要另行核对。经过整理的教学对话要明确标注；不得把设计的顺利过程写成真实试做记录。

## 结果与练习：把「做出来」写具体

案例的完成标准以各 [案例说明](../examples/README.md) 为准。正文引用这些标准，不另设一套含义不同的「完成」。区分预期结果与实际结果，写出仍需人工处理的部分。

练习应给读者一次作出选择的机会，例如替换一批材料、修改一条规则，或发现并解释一个结果差异。提供可独立核对的依据，不只展示程序自己生成的成功提示。

反复使用时暴露的问题也是内容：新分类、缺失字段、长文件名或版式变化，可以说明旧规则哪里不够。只写已观察到的失败原因；证据不足时保留可能性。

## 写作示例：从笼统建议到可判断的论述

以下片段为教学写作示例，不代表工具已经实现或案例已经通过试做。

笼统表达：

> 利用 AI 智能更新汇报，检查无误后即可完成自动化，提高工作效率。

改写示例：

> 每个月的汇报版式相同，变化的是表格里的数据。第一版可以先只更新一页。把这一页要用的单元格和 PPT 中对应的位置说明白，才有办法判断程序有没有填对。
>
> 生成这一页后，把其中的数字与输入表格逐项核对，再检查文字有没有挤出文本框。如果数字不同，先保留输入表格和生成的 PPT，记录哪一项不一致。找到差异之前，先不要扩大到整份汇报。
>
> 一页做对，只能说明这组材料下的结果符合要求。换一批数据后，还要重新核对。重复使用时能否保持正确，决定了这个工具是否适合进入日常工作。

改写交代了范围、判断依据和继续操作的条件。它保留「为什么先做一页」的解释，也没有许诺尚未测量的效率收益。
