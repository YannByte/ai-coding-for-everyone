# 本书的写作方法

本书借鉴 ASD-STE100 的受控语言原则：让读者用较少的猜测理解作者的意思。这个方法用于全书的论述、案例、操作、练习和翻译，也用于配套文档。写作的目标是帮助读者作出判断，并高效使用 AI 编程助手完成软件开发任务。

## 参考依据与本书的取舍

ASD-STE100 面向英文技术文档，由写作规则和受控词典组成。词义明确、术语稳定，是它减少歧义的重要方法。参见 [官方说明](https://www.asd-ste100.org/about_STE.html) 与 [官方 FAQ](https://www.asd-ste100.org/STE_faq.html)。

本书参考 [Issue 9](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf)（2025 年 1 月 15 日）的规则与词汇方法。2026 年 10 月 17 日对照了句子、操作、说明、注意事项和一致性相关条款，以及少量词典条目；具体取舍见 [对照记录](ste100-review.md)。这次核对不等于审查了全部标准条款。

以下是本书根据读者和案例制定的写作约定，不是标准条文的翻译。中文不套用英语词典、词性或词数限制；英文版本也不因采用这些约定就宣称完全符合 ASD-STE100。中文表达与排版另见 [中文写作规则](chinese-writing.md)。

执行顺序、工作状态和证据记录见 [写作工程流程](production.md)。已确认的项目决定继续生效，不从空白提示词重新规划。

## 按任务使用

这些规则适用于正文、案例、练习和翻译。开始前读取 [项目定位](project.md)、[全书脉络](../book/zh-CN/README.md) 和目标目录的 AGENTS.md。

| 任务 | 执行范围 |
| --- | --- |
| 起草 | 按本文件准备并完成正文，标明证据和试做缺口 |
| 改写 | 修改用户指定范围，保留事实、逻辑、限制与确定程度 |
| 校对 | 只处理指定的错字、标点或术语，不自行重排整章 |
| 审稿 | 按 [审稿规则](review.md) 记录问题；仅审阅时不修改正文 |
| 翻译 | 同时执行 [翻译规则](../translations/AGENTS.md)，记录原文版本与审阅状态 |

起草或改写后，使用审稿规则检查交付内容。规则不预设章节数、篇幅或固定叙事模板。

## 先分清这段文字的用途

论述解释为什么这样判断，可以保留叙事、取舍与失败过程。操作段告诉读者现在做什么，要写清执行者、对象、条件与检查办法。证据段说明谁在什么条件下观察到了什么，不能把教学设定写成运行记录。

三类文字可以出现在同一章，但转换时应让读者看得出来。例如，先解释为什么需要原始样本，再写「请助手用这份样本运行程序」，最后展示标明性质的结果。不要把整章改成命令，也不要让必须执行的动作埋在背景解释中。

## 写作前：先说明读者要解决什么

每章起草前，写清以下五项。可以放在章节草稿的写作说明中，正式正文不必照抄这些标签。

| 项目 | 写清什么 |
| --- | --- |
| 工作问题 | 读者手里有什么材料，原来怎样做，具体卡在哪里 |
| 本章判断 | 读完后，读者应该能作出哪一个判断 |
| 本章结果 | 读者能完成什么，怎样看出是否完成；概念章可以是明确范围或判断标准 |
| 必要知识 | 读者已经知道什么，还需要在本章解释什么 |
| 证据与缺口 | 哪些来自真实来源，哪些是教学设定，哪些还没有试做 |

一个章节可以包含多个环节，但应共同支持本章判断。不能只用功能清单、提示词数量或代码长度说明章节价值。

## 论述：让读者看见判断怎样产生

从具体工作进入问题，再说明可选做法、选择理由和适用条件。案例结果要能支持本章判断；结果尚未验证时，保留设计状态。

每段围绕一个主要意思展开。需要连接原因、条件或转折时，写出关系。不要为了缩短句子删掉「如果」「因为」「但」后面的必要说明。可以用长短不同的句子，也可以直接称呼读者为「你」。

用读者熟悉的对象解释概念。例如，先说明「助手修改了需求之外的文件」，再解释任务边界、代码差异和审查依据。术语首次出现时说明用途；后文采用 [术语表](terminology.md) 的同一表达。

可单独阅读的样章和问题入口，应补足本次判断需要的最小解释。例如，要求读者核对测试时，先解释测试检查什么，再说明看哪些实际结果；不要只用另一个陌生词解释它。需要前文操作基础时给出已有入口，前文尚未完成时如实说明。词表是作者的依据，不能代替正文中必要的解释。

使用明确的执行者和动词。「让 AI 编写读取表格的程序」与「程序读取表格」描述不同环节，不能都写成「AI 处理数据」。把「优化一下」「智能整理」「处理完成」改成读者能够观察或判断的内容。

案例中的重复工作、判断困难和失败过程可以保留叙述。比喻可以帮助理解，但要交代它与实际机制的边界。自然语气与准确表达同时保留。

简化时先拆开叠在一起的概念，再考虑缩短句子。保留连接原因、条件和结论的词；不把连贯论述切成没有关系的短句。连续技术名词先写出关系，例如把「项目状态验证」展开为「将交接记录与当前文件对照」。

## 精简：每段都推进论述

以第 9 章 [精简稿](../book/zh-CN/09-choosing-libraries-with-an-agent.md)（提交 `d32f63f`）的密度为参考，不设固定字数或删减比例。

- 收到补充想法时，先判断它能替换哪段解释、补强哪个判断，优先融入已有论述。只有现有结构无法承载且确有必要时才新增小节；配套文件只同步受影响的事实、证据和版本，不把局部补充扩展到项目定位或全书结构。
- 同一观点讲透一次。后文再次出现时，应增加条件、证据、选择或结果；删除换一种说法重讲的段落，以及开头、段末和结尾的反复总结。
- 原理解释到足以支持当前判断。保留具体案例，删去不影响本章选择的知识旁支；来源链接就近保留，研究过程放入材料卡。
- 提示词只展示影响结果的必要信息。正文已经说清的要求，不再用长提示词完整复述；也不在提示词之后逐句重讲。
- 教学设定、候选状态等共用说明集中交代。影响某次操作的条件、权限和停止要求仍放在操作前，不能为了精简删掉。

精简后仍须讲清为什么、怎么做、怎样判断结果。保留新手需要的概念解释与因果衔接，不把正文压成提纲或连续短句。

## 写清 AI 怎样参与这项工作

全书的案例、操作和对话，默认读者正在与具备执行能力的 AI 编程助手交流。助手通过工具读取材料、改变文件、运行程序，把执行反馈带入后续判断。一次请求可以包含多轮调查、执行和检查，不需要读者每一步都发出新指令。写作要呈现它围绕目标持续工作的过程，不能只给通用操作步骤换上「让 AI 做」的主语。

分工须落在具体情境里：读者说明目标、必要限制和只有自己知道的信息，提供访问条件，核对实际用途；助手承担权限与能力范围内的调查和执行。能从已有文件、项目说明和工具反馈查明的信息，由助手先查；不要默认让读者先挑好每份材料、设计搜索步骤、逐条输入命令，或在程序与助手之间搬运每次报错。需要读者介入时，说明缺少的是权限、意图、判断还是助手无法执行的操作。读者可以随时提问、纠正或停止任务。

验证也是助手工作的组成部分。条件具备时，让它运行检查、重现问题，或通过浏览器操作、截图和日志核对结果，发现问题后继续调整。读者判断结果是否符合自己的用途，不必接手所有技术检查。区分「助手说完成了」「留下了哪些验证材料」和「实际问题是否解决」；缺少独立依据或尚未检查的部分，要如实保留。

起步只要求一台电脑和一个可用的编程助手。命令行、编程环境与依赖在实际需要时由助手先检查和处理，解释随问题出现；必须由读者操作的部分，再写清位置、动作与预期结果。不把这些知识和工具变成开始对话前的学习清单。

上述方法面向各种编程助手，正文采用 [术语表](terminology.md#面向读者的称呼) 中的通用称呼，不默认读者只使用 Codex、Claude Code 或其他某款产品。能力取决于当前工具、运行位置、模式和权限，不能仅凭产品名称判断；例如，云端任务未必能读取电脑里的文件，只做规划的模式未必能修改文件。产品差异在影响当前任务时说明，具体操作与实测记录标明产品和版本。官方资料说明产品支持什么，实际执行记录说明这次做了什么，两者不能互相替代。工作方式的依据见 [来源记录](sources.md#现代编程助手的工作方式)。

让对话和执行反馈带着问题往下走。对话用于表达需要、补充信息和调整方向，不必写成人与助手轮流推动每一个动作；助手也可以持续执行或在后台工作，再带回结果与待判断的问题。解释放在读者真正卡住或需要判断的位置，不把每段对话都写成提示词模板，也不在之后逐句总结道理。

通用的软件开发原则可以保留，但要解释它在使用 AI 时怎样落实。例如，检查一个推荐是否有实际查阅记录，或检查助手的下一步是否采用了刚得到的运行结果。不要把这些原则宣称为 AI 独有，也不要靠新增模型、记忆、多 Agent 等名词制造区别。教学过程仍须标明未实测，能执行的范围以实际工具和权限为准。

## 复用：解释为什么不用 AI 从头实现

按 [项目范围](project.md) 的复用方式安排内容。复杂或需要长期打磨的能力，先让助手调查现成项目、配置和扩展方式、成熟库，再明确需要新增的代码。不要把「充分利用开源」缩成列出几个库名，也不要把少写代码作为唯一目的。

解释三者的区别：模型根据所获信息生成代码，助手通过执行获得反馈，已有项目通过实际问题、修复和测试积累边界处理经验。生成完整、演示成功、少量测试通过，都不能证明已覆盖实际使用条件。用具体材料说明遗漏怎样发生，以及复用能沿用哪些已有处理；不能仅凭模型原理推断某段代码必定出错。

调查要有维护、兼容性、测试与许可依据；接入后仍需检查自己的输入、调用方式及完整用途。优先配置、调用和必要扩展，改动原项目时说明后续更新成本。没有合适实现或简单自写更合适时，保留理由。不要宣称开源必然成熟、可以免测，或永远不应写新代码。

## 操作：让读者知道下一步做什么

只在确实需要读者动手时使用步骤。按实际执行顺序组织，写清以下内容：

1. 交代开始前需要的文件、工具状态和条件。涉及覆盖、删除或上传时，在动作前说明对象与后果。
2. 每个步骤给出一个主要动作。写明对象；有多个相似对象时，用名称区分。必须依次执行的动作拆开；需要同时执行的动作和紧随动作出现的结果，可以留在同一步。
3. 区分读者的操作、AI 的回复和程序的行为。程序自动完成的事不写成读者要执行的指令。
4. 在需要判断是否继续的位置，说明预期结果和核对办法。
5. 结果不符时，说明先停止什么、保留什么，以及依据哪些现象继续检查。

条件、操作和结果必须有来源或试做依据。缺失内容标记为待试做，不能为了补全步骤编造按钮、路径、耗时或恢复方法。发布练习前，应补齐这些缺口。

必做动作、权限范围、输入限制和停止条件写在操作正文中。脚注、提示框和延伸阅读用于补充解释。审稿时暂时遮住这些补充内容，检查操作是否仍完整；若必须靠附注才能做对，把必要信息移回正文。

核对条件的逻辑范围。「只有检查通过才可继续」不等于「检查通过后立即继续」；「至少一项满足」不等于「全部满足」。改写和翻译保留必要条件、否定对象、先后次序和数值边界。不能为了主动句补造未知的执行者。

对实际涉及的覆盖、删除、上传或费用，在相应操作前说明具体对象、后果和可用的保留办法。不要用「小心操作」代替说明，也不为没有相关风险的段落增加通用警告。

## 提示词与对话：说明表达需要的方法

展示提示词时，交代当时已有的文件、读者的目标和不能改变的要求。随后解释提示词中的哪些信息影响了结果。读者应能替换自己的材料和规则，而不只是照抄一段话。

AI 回复只作为当次回复的记录。代码、文件和实际结果需要另行核对。经过整理的教学对话要明确标注；不得把设计的顺利过程写成真实试做记录。

## 结果与练习：把「做出来」写具体

案例的完成标准以各 [案例说明](../examples/README.md) 为准。正文引用这些标准，不另设一套含义不同的「完成」。区分预期结果与实际结果，写出仍需人工处理的部分。

练习应给读者一次作出选择的机会，例如替换一批材料、修改一条规则，或发现并解释一个结果差异。提供可独立核对的依据，不只展示程序自己生成的成功提示。

「检查结果」必须能对应到可见材料：在哪个文件或界面看，预期是什么，实际是什么，不符时先做什么。读者不必读懂全部实现才能核对文件名、数量或内容。输出摘要有帮助，但不能替代它所声称检查过的结果；预期也不能直接抄自本次输出。

反复使用时暴露的问题也是内容：工具超时、重复执行、缺失信息或旧状态，可以说明旧规则哪里不够。只写已观察到的失败原因；证据不足时保留可能性。

## 连续论述与问题查阅

主线按读者使用现成 AI 编程助手完成软件任务的顺序展开，故障与恢复过程支持当前阶段的判断。不要把使用问题转写成实现 Agent 内核、工具框架或评估平台的教程。每章讲清为什么、怎样做、做完检查什么；不能以知识点是否新颖或是否被其他书覆盖作为唯一选材标准。问题索引引用实际章节，不再复制一套正文。

本组织方法参考子木的 [小册子前言](https://bysocket.com/saas-seo-playbook/00-01-why-this-book/) 与 [主题规划](https://bysocket.com/saas-seo-playbook/05-keyword-research-to-topic-map/)。只借鉴读者、任务和章节的组织关系；商业转化目标不作为本书教学目标。

## 英文与多语言

英文使用自然、具体的表达，兼顾英语非母语读者。同一专业概念保持稳定，普通词不必逐词对齐中文。自然的缩写形式和动词用法可以保留，例如 don't 和 check the result；本书不采用 STE 的全部词性、时态或缩写限制。

STE 的操作句 20 词、说明句 25 词和段落 6 句限制，在本项目中仅用作英文审阅提示，不是交稿门槛，也不换算成中文字数。拆句后必须检查条件是否仍与动作相连、段落是否连贯。详细词汇取舍见 [词汇约束](terminology.md#词汇约束与程序检查)。

翻译可补上目标读者需要的解释，但要在状态或审阅记录中说明增补。代码、路径和界面名称保持真实；解释性标签与实际标识分开。译文与原文的版本关系由 [翻译清单](../translations/manifest.json) 记录，语言等价和读者理解仍需人工审阅。

## 写作示例：从笼统建议到可判断的论述

以下是教学写作示例，不代表已完成试做，也不确定教学项目。

笼统表达：

> 让助手修复问题，运行测试后即可交付，提高开发效率。

改写示例：

> 先把问题出现的条件、预期结果和实际结果交代清楚。请助手查找相关实现，并用代码位置或可复现的现象说明它判断的原因。原因还没有依据时，先补充检查，避免直接扩大修改范围。
>
> 修改以后，核对代码差异是否对应原问题，再检查原来的失败是否消失、相关功能是否仍能工作。助手回复「已修复」只能作为说明，实际测试和差异才是验收材料。测试没有运行或条件不满足时，要把这部分缺口保留下来。

这个示例交代了读者如何指导和检查一次修复。效率改善还需要结合人工介入、等待与返工等记录判断，不能由一次成功回复推断。
