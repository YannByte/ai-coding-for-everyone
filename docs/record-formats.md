# 写作与验证记录格式

记录随实际工作创建，不预填成功结论。公开记录只保留经过整理、无私人信息的内容。原始访谈与未获授权的工作文件按 [公开范围](publication-scope.md) 处理。

## 证据条目

[证据清单](../book/evidence.json) 中每条记录包含唯一 `id`、具体 `claim`、`kind`、`status`、`source`、`locator`。`source` 为公开网址或仓库内文件路径；`locator` 指向标题、页码、原文段落或记录位置。`pending` 时允许 `source` 或 `locator` 为空。

核实后仍需说明范围，例如「作者自述每月重复制作」不写成「所有人每月都遇到」。设计（design）使用 planned 状态，不能标为 verified 后伪装为实际结果。

## 试做记录

正文尚未起草时，可以先完成案例试做，记录案例与材料版本。正文形成后，再核对文字能否准确复现试做过程，并登记与正文版本绑定的 author-trial 记录。不要为了取得正文哈希而推迟素材验证。

每次作者或读者试做使用一份 Markdown 记录，至少包含：

- 对象与版本：任务 ID、正文版本、工具与环境、输入文件和独立对照结果的路径；文件在后续变化时保留原版本依据。
- 工作目标与原来做法：完整工作步骤、现成工具的可行路径。
- 实际操作与结果：成功、错误、遗漏、版式问题以及恢复过程，关联输出文件。
- 人工投入：准备、运行、检查、返工和维护分别记录；没计时就写未测量。
- 参与者背景与帮助：用匿名标识，说明编程经验及现场帮助；作者试做不能记成读者试做。
- 再次使用：新一批材料、改变的规则、是否能迁移，以及仍需人工处理的部分。
- 结论与限制：pass 或 needs-work；只对本次版本、环境和材料作出判断。

实践章节的 reader-trial 记录还应说明：读者能否复述判断依据、跟做是否完成、换材料后是否能继续。人工辅导过的步骤必须说明。论述章节的 reader-review 只评价理解，不宣称完成实践。

## 审阅记录

正文首次创建后，在 `book/reviews/` 中按任务与日期创建记录。每份写清任务、审阅类型、审阅者（作者、AI 或读者）、正文 SHA-256、结论、问题位置、修改建议和剩余限制。类型为 structure、facts、language、author-trial、reader-trial 或 reader-review。

通过记录在 [工作状态](../book/workflow.json) 的 reviews 中登记 kind、result、report、manuscript_sha256。文件哈希可在仓库根目录运行以下命令取得，把示例路径替换为实际正文路径：

```sh
python3 -c "import hashlib,pathlib; print(hashlib.sha256(pathlib.Path('book/zh-CN/chapter.md').read_bytes()).hexdigest())"
```

不要只更新哈希沿用旧结论。修改正文后复核影响，保留原记录并建立新的记录；未完成复核时退回 revising。

结构审稿先检查论点、材料与顺序；事实审阅逐条查证据；语言校对最后进行。整稿审阅只提供成稿和读者能获得的配套资料，另行报告书的整体问题。
