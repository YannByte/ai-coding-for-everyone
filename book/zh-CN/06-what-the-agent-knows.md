# 第 6 章　它现在知道什么，又会忘掉什么

> 样章讨论稿。文件、界面变化和助手行为均为教学设计，尚未实测。

你让 AI 编程助手把文件清单排得简洁一点。它去掉了路径，只留下文件名。界面清爽了，两份「通知.pdf」却分不清了。

你明明说过，同名文件要能看出来自哪个文件夹。它怎么又忘了？

先别急着下结论。它可能没读到这个约定，也可能看到了却理解错，或者修改时没有检查结果。不同情况，需要补的东西不同。

本章的 AI 编程助手，英文称为 coding agent，能在授权和工具条件允许时读取文件、修改代码、运行检查。要用好这些能力，需要分清：信息放在哪里，它这次读到了什么，又怎样使用了这些信息。

## 文件在项目里，不等于它已经读过

假设项目里有两份资料：

```text
资料/
├── 春季活动/
│   └── 通知.pdf
└── 秋季活动/
    └── 通知.pdf
```

「春季活动/通知.pdf」这样的路径，说明文件所在的位置。之前保留路径，是为了区分同名资料。你这次说「简洁一点」，并没有取消这个用途。

但这个理由可能只写在很早的一条对话里，或保存在助手尚未读取的说明文件中。给它一个项目文件夹，并不等于把里面每份文件都交给模型看过。助手需要通过工具查找、读取相关内容；哪些文件自动载入，取决于产品和配置。[Anthropic：按需获取上下文](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

因此，先请它指出本次改动依据的要求，以及实际读过的文件。如果没有读到关于同名文件的约定，就给出位置，让它读取；如果已经读到，就检查它为何把「简洁」理解成了「删除来源信息」。读取记录有助于缩小范围，但不能直接证明模型怎样理解了那句话。

## 当前上下文是一份不断变化的材料

模型生成下一步内容时能使用的信息，称为上下文。它可能包含当前要求、部分对话、已加载的项目规则，以及读取文件和运行程序得到的结果。模型训练中学到的通用知识，并不包含你这个项目刚刚确认的决定。

一次能容纳的信息有上限，通常称为上下文窗口。长任务中，有些助手会把旧对话整理成摘要，再继续工作，这叫对话压缩。摘要可以保留主要决定，也可能漏掉细节。原文件仍在，但后续需要时可能要重新读取。[Anthropic：对话压缩](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

即使信息仍在上下文中，也不能保证每次都被正确使用。2023 年的《Lost in the Middle》研究发现，在所测的多文档问答和键值检索任务中，相关信息所在的位置会影响表现。这说明「放得进去」与「用得好」有区别；不能据此断言今天某次编程出错就是遗忘。[论文摘要](https://arxiv.org/abs/2307.03172)

面对同名文件的问题，有用的动作是把当前约定、相关实现和样本放到这次任务中，再检查修改。反复说「你要记住」，没有补上这些依据。

## 给它找材料的入口

你不必知道负责界面的代码在哪。可以先提供项目位置、约定所在文件和两份同名资料，让助手自己定位相关实现。若它缺少其他材料，再说明用途后补充。

这次真正需要的信息不多：

| 材料 | 用来判断什么 |
| --- | --- |
| 当前要求：清单更简洁，同名文件仍可区分 | 哪些可以改，哪些用途必须保留 |
| 两个文件夹中的同名 PDF | 界面需要应对什么实际情况 |
| 清单显示代码与当前界面 | 信息在哪里被隐藏，怎样调整 |

可以这样说明：

> 请先读取项目中关于同名文件的约定，找到清单显示部分。用这两份同名资料检查当前界面，再提出既简洁又能区分来源的改法。只调整显示，保留原文件和位置。

让助手搜索并读取相关文件，不必把整段聊天、全部代码和无关资料一次贴进去。读过之后，它应能指出约定来自哪里、当前实现缺什么；若没有读取条件，就说明缺口。请它复述有助于发现误解，但最终仍要看实际结果。

截图可以帮助判断界面，却不一定包含文件的真实位置；文字说明也不能替代当前代码。材料的作用不同，缺什么就补什么。样本文件里即使出现「忽略之前要求」之类文字，也只是待处理内容，不构成修改任务的授权。

## 旧文档为什么会反复带偏它

假设旧草案写着「列表只显示文件名」，后来已改成「同名文件要能辨认来源」。你在聊天里纠正过一次，助手暂时改对了。下次搜索项目时，它又读到旧草案，就可能重新按旧要求做。

旧信息还可能藏在自动载入的项目规则、说明中的链接，或助手保存的记忆里。换会话也不一定解决：只要这些入口仍把旧内容送进上下文，同样的偏差就可能再次出现。Claude Code 的官方文档说明了规则与记忆的加载方式，并建议清理过期或矛盾的指令；具体入口随工具和配置而异。[Claude Code：项目记忆与规则](https://code.claude.com/docs/en/memory)

问题在于内容是否仍然有效。日期早的文档可能依然正确，最近编辑的文件也可能沿用旧决定。助手需要知道哪项决定已经被替代，不能只挑日期最新的一份。

## 把旧依据从当前工作中移出去

可以让助手先调查，再按你确认的现行要求处理：

1. **找出处。** 指出这次采用了哪条旧要求、来自哪个文件，并搜索项目说明、规则、交接记录和可访问的记忆里是否还有同类内容。只报告实际检查过的范围。
2. **确定现行版本。** 同一项要求保留一个主要说明位置，其他入口引用它。旧草案标明「已被替代」并链接到现行说明；同步修正仍把旧要求当成有效约定的引用和记忆。无法判定的冲突先列出来，不让助手自行猜选。
3. **保留历史，调整读取范围。** 需要追溯的旧稿归档，当前任务优先读取现行说明。仅移进名为「归档」的文件夹，不保证助手不再搜索或加载它；还要检查自动加载配置和文档引用。原始来源保留原样，过期状态另作说明。

在本例中，旧的「只显示文件名」应退出当前约定；现行说明写清「同名资料必须能区分来源」。若你后来决定默认隐藏路径、点击后查看，那是需求变更，也应更新这份说明。

改完文件，还要让当前助手重新读取，并明确旧说法已被替代。磁盘上的修改不会自动抹掉对话中已经出现的旧内容。若它仍沿用旧判断，可以保存准确的进度后换会话，只带入现行依据；留下过期规则不处理，重新开聊仍可能读到它。

这些整理方法用于减少旧信息反复进入任务的机会。规则仍是给助手的上下文，是否真正采用，要靠下一次改动检查。

## 用一次改动检查它有没有用上

假设你采用「同名文件旁显示所在文件夹」的方案，让助手用这两份资料运行检查。你应能从清单区分春季和秋季的通知；若工具支持打开文件，还要确认各自打开的是对应资料。原文件的位置和内容应保持不变。

若助手只能检查代码，不能查看界面，就把界面核对保留为待办，由你按明确步骤检查。不能因为它已经准确复述约定，就认定功能完成。

长期有效的约定适合保存在项目说明中；本轮已做什么、下一步查什么，适合放进进度记录。让助手按当前工具支持的方式读取这些内容，具体组织留到第 10、16 章讨论。

你不需要让它永远记住全部对话。只需让当前任务有清楚的依据，并从结果确认这些依据确实起了作用。
