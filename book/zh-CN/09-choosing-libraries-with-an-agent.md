# 第 9 章　先找成熟实现，再让 AI 补上需要的部分

> 样章讨论稿，修订中。文件搜索需求、样本和操作示例均为教学设计，尚未实测。文中提到的库是调查候选，不代表已为本书项目完成选型。

文件清单已经能列出资料，但你想找的是正文里的一句话。文件名叫「通知」「附件」「修改版」，光看名字，仍不知道该打开哪一份。

于是，你请 AI 编程助手加一个搜索框：输入「报名截止」，把包含这几个字的 PDF 找出来。

接下来，它可能很快写出一批代码。界面有了，按钮也有了，拿一份通知试一下，也搜到了那句话。可是换成扫描件、带密码的文件，或者排版不同的资料，还能得到可信的结果吗？这些偏离顺利演示、却会在实际使用中遇到的情况，就是这里说的边界情况。

做这样的功能，值得先让助手调查已有实现。尤其是处理复杂格式、需要长期打磨的部分，尽量复用有维护和测试依据的开源代码，再补自己的需求。这样有机会沿用别人已经处理过的边界情况，减少从头发现和修补同类问题的工作。

本章使用的 AI 编程助手，英文称为 coding agent，可以在授权范围内读取项目、修改文件和运行检查。查找现成项目、阅读文档和代码、配置或修改，以及验证结果，都可以交给它。具体能执行哪些工作，取决于工具和运行条件。你不必先学会搜索一串陌生的技术名称。

## 为什么写出来还不够

你说「找到包含这句话的 PDF」，表达了目的，却没有列出所有输入情况和失败时的处理方式。助手可能想到一部分，也可能遗漏一部分。假如它只拿能提取文字的文件试运行，就没有证据说明扫描件也能处理。要求中没有写出的条件、程序里没有实现的处理、检查时没有覆盖的样本，是三个不同的缺口。

从模型这一层看，语言模型根据训练中学到的模式和当前获得的信息生成代码。生成过程本身并不等于逐一运行所有可能的输入，也不构成程序正确性的证明。早期代码模型研究就将生成代码与执行测试分开，用运行结果评价功能是否正确。这里借用的是这个区分，不把 2021 年模型的成绩用于评价今天的编程助手。[Chen 等：Evaluating Large Language Models Trained on Code，第 2 节](https://arxiv.org/html/2107.03374v2)

当前获得的信息，也叫上下文，包括你的要求、助手读过的文件、文档和工具返回。模型可能从训练中知道某种异常情况，但这不保证它会在当前任务中正确处理；它也不会因为你给了一个项目文件夹，就自动读完其中的所有内容。Anthropic 的工程文章强调，上下文需要选择和管理，助手可以通过工具按需补充信息。这意味着你可以请它主动查找限制，而不必独自把所有例外写成一条长提示词。[Anthropic：上下文工程](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

AI 编程助手还能运行程序，根据结果继续修改。这比只生成一段代码多了反馈，但反馈能纠正什么，取决于它实际做了什么检查。如果写程序和写测试时都假定「PDF 里一定有可提取的文字」，两边就可能遗漏同一种情况。让助手再检查一遍有用，但还应补进来自真实资料、官方限制说明或已有项目测试的不同依据。

成熟开源实现的价值，就在这里。一个持续处理实际问题的项目，有机会把不同用户遇到的异常变成修复，再保留成自动测试：给程序指定输入，检查输出是否符合预期。以后修改时再运行这些检查，帮助发现旧问题是否重新出现。以 pypdf 为例，它的开发文档说明了 PDF 样本测试，并要求针对旧问题的测试标明对应的问题编号。这是可查的工程积累；它不证明所有 PDF 都已覆盖。[pypdf 测试文档](https://pypdf.readthedocs.io/en/stable/dev/testing.html)

因此，复用的价值包括现成的处理逻辑，以及支持这些逻辑的样本、测试和已知限制。让 AI 凭描述重新写一个功能相似的版本，并不会自动带上这些积累。即使模型在训练中见过相关代码，也不等于这次生成的版本完整保留了那些修复。调用合适版本的库，可以沿用其中已有的处理；你仍要检查调用方式和自己的使用场景。

开源也不等于成熟。只公开了代码、没有维护和验证依据的项目，不能因为可以下载就被当成可靠基础。这里推荐的是优先调查和验证已有实现，而不是保证开源代码一定比新代码好。

## 先判断哪些部分已经有人做好

开源软件按其许可提供使用、修改和分发代码的权利；实际能怎样使用，要看具体许可。GitHub 上能看到代码，不代表可以任意拿来改用。[GitHub：仓库许可说明](https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository)

复用可以从完整软件开始。如果已有的开源搜索工具能处理你的资料，先让助手帮助配置，再核对结果。缺少某个显示选项时，可以调查能否通过配置或扩展补上，不必立即重写整套搜索功能。

如果需要保留自己已有的文件清单，就调查其中哪些能力可以接入。程序可调用的现成组件，通常称为库。例如，把 PDF 文字提取交给合适的库，让助手编写连接文件清单、搜索结果和页面显示的代码。连接部分也需要验证，但可以把重新开发复杂格式处理的范围缩小。

还有一种情况：现成项目已经接近需要，却没有可用的配置或扩展方式。可以让助手阅读相关实现，评估小范围修改。若为了一个小需求必须大改原项目，后续跟随原项目更新也会更费力，就要比较换一个方案是否更合适。

这几条路径不必全部走一遍。调查应回答一个具体问题：已有实现负责什么，我们还需要补什么？对于规则简单、范围明确的小功能，自己写可能更直接；对于需要长期处理各种格式和异常的部分，应先说明为什么现成实现不适用，再决定从头开发。

## 先说清楚要找什么

「给 PDF 加搜索」还不够具体。按文件名查找、查找正文中的连续文字、理解一句话的意思后寻找相关资料，需要的处理不同。

这个教学情境先限定为：在指定文件夹的 PDF 中查找连续文字「报名截止」，列出文件位置、所在页和附近的一小段原文。资料在本机处理，不改动原文件。暂不要求理解同义表达，也不把跨行断开的文字自动拼成同一次匹配。

你不必一开始就把这些要求写全。可以先告诉助手：「我记得某份资料里有『报名截止』，但不记得文件名。」请它读取项目，找出实现这个目标还缺哪些信息，再用你听得懂的问题确认。例如，是查准确的文字，还是查意思相近的内容？资料中有没有扫描件？这些答案会改变它要调查的方案。

助手需要把日常说法转成可查证的技术要求，再解释这些要求怎样影响使用。你核对的是它有没有理解错目的。例如，只要按文件名筛选，就未必需要读取 PDF 内容；希望扫描件也能搜出来，就不能只看普通文字文件上的演示。

把目的交代清楚后，可以请助手先看现有项目：有没有已经能用的实现？现有软件能否完成这项任务？是否只需补少量代码？如果项目使用 Python，列出文件夹中的文件，就有 pathlib 这样的标准库能力可查。标准库是随语言官方实现提供的组件，不需要为了同一件事再找一个第三方库。[Python 官方 pathlib 文档](https://docs.python.org/3/library/pathlib.html#pathlib.Path.rglob)

## 让助手查明能复用什么、还缺什么

调查之前，还需要认识一个词：依赖，也就是项目需要的其他软件包。新增一个库，通常也意味着项目以后安装、运行和更新时要继续考虑它。助手应当查看项目已经有什么，再决定缺什么。

把项目位置和已准备好的资料副本交给助手后，可以请它这样调查：

> 请先阅读项目，确认现有实现和依赖能做哪些事。我想按 PDF 正文中的连续文字搜索，并看到文件位置、页码和原文片段；资料只在本机处理。先调查已有项目、可配置的软件和库，说明哪些能力可以直接复用，还缺哪些功能。请查官方文档和相关测试，解释建议采用什么、已处理哪些边界、哪些资料仍处理不了，以及怎样用我的样本核对。不要默认从头实现 PDF 解析或文字识别。保留来源链接与版本信息。这轮先给调查结论，不修改项目。

这一步需要它实际读取项目文件和当前文档。可以请它在结论中指出：从哪些文件看到了现有依赖，查阅的是哪个版本的文档，哪些内容仍未核实。知道一个库的名字、能写出一段用法，并不能说明它已经核对过你的项目。没有联网或读文件的条件时，就保留待查项，不能把回答写成已经完成的调查。

如果它返回十几个项目或库名，每个后面都写着「功能强大、使用方便」，调查还没有结束。可以继续问：你建议先试哪个？为什么适合这个项目？哪一个限制可能直接影响我的资料？

下面沿着「保留现有清单，接入文字提取库」这条路径继续说明。它是教学设定，不表示已排除完整工具或其他方案。假设助手提出 pypdf。它的官方文档确实列出了 PDF 文字提取能力，这足以让它进入候选范围。但它能否处理这批资料、接入现有项目是否合适，仍要另外检查。[pypdf 官方文档](https://pypdf.readthedocs.io/en/stable/)

还应让助手核对包名与官方项目是否对应、近期发布和维护记录、当前环境是否支持，以及许可对计划中的使用和分发有什么要求。读者需要的是这些事实怎样影响当前决定。来源缺失就标为未核实，不能用一句「这是成熟方案」结束调查。

成熟也不等于适合。一个项目或库即使能完成许多复杂工作，如果这次只需要其中很小的一项能力，额外的安装和维护负担仍然要算进去。助手可以比较方案，但不必为了显得全面，把所有候选都安装一遍。

## 最重要的限制，可能藏在「支持 PDF」里

肉眼看起来相似的 PDF，内部内容可能不同。有的文件包含可以提取的文字，有的页面只有文字的扫描图像。从图像中识别文字的技术叫光学字符识别，英文简称 OCR。pypdf 的官方说明明确区分文字提取与 OCR：它不能从图像中识别文字。扫描件也可能已有文字层，不能仅凭「看起来像扫描件」判断它一定无法提取。[pypdf：文字提取与 OCR](https://pypdf.readthedocs.io/en/stable/user/extract-text.html#ocr-vs-text-extraction)

这会直接改变搜索结果的含义。

假如一个页面没有提取出文字，程序随后告诉你「没有找到报名截止」，你很容易把它理解为这份资料没有这句话。但程序可能根本没读到页面上的字。

因此，可以要求助手保留两类不同的信息：一类是「已提取的文字中没有匹配」，另一类是「这部分内容未能完成检索」。后者要列出文件和页码，供后续处理，不能悄悄从结果里消失。

这里还不能走到另一个极端：提取结果为空，不足以单独证明页面就是扫描图像；提取到少量文字，也不能证明整页内容都已读到。让助手保留实际提取情况，说明没有检查过哪些内容，比替每份文件猜一个原因更有用。

对于经常处理扫描资料的人，这个限制可能足以改变选用决定。如果主要资料都需要 OCR，就应重新调查相关方案。不能先接入一个不覆盖主要需求的库，再把大多数文件留给读者手工查找。

## 先拿自己的材料做一次小验证

看过官方演示以后，下一步可以请助手做一个独立的小程序，只验证读取和查找能力。先保存当前项目，在另一个工作目录里使用资料副本，约定输出位置，不覆盖已有文件。安装所需软件时遵守已有授权；超出范围的操作先说明影响。

这轮可以暂时不做搜索界面。让助手把样本读取、结果展示和检查连起来：自己编写验证程序，运行后读取输出，再决定是修改调用方式、补查文档，还是报告当前方案不适用。你给出样本和预期，它负责把检查执行出来。Claude Code 的官方说明将这种工作方式描述为收集信息、采取行动、验证结果，并根据工具返回继续处理任务；具体能力仍取决于工具和权限。[Claude Code 的工作方式](https://code.claude.com/docs/en/how-claude-code-works#the-agentic-loop)

为了说明检查方法，这里设计三份单页资料。它们不是已提供的练习附件，表中的要求也不是运行结果。

| 样本 | 人工预先知道的内容 | 希望检查什么 |
| --- | --- | --- |
| 活动通知.pdf | 可提取的文字中有「报名截止」 | 能否返回正确文件、第一页及对应片段 |
| 材料说明.pdf | 可提取的文字中没有「报名截止」 | 是否出现错误匹配 |
| 旧通知扫描.pdf | 只有扫描图像，肉眼可见「报名截止」，没有文字层 | 仅做文字提取时，能否明确列为未能检索，而不是声称不存在关键词 |

在真正准备样本时，你先打开文件，核对内容，再请助手运行。可以让它逐份展示提取出的文字、匹配结果和无法处理的部分。预期应来自文件本身，不能把程序第一次输出的内容直接拿来当答案。

这一轮还有一个容易混淆的地方：助手直接看图读出了「报名截止」，不等于它写的搜索程序具备同样能力。请它指出结果是由哪一次程序运行产生的，并留下实际输出。如果程序只提取了空文字，而助手在回复里补出了答案，仍不能据此确认程序可用。

小验证的价值，是让方案有机会被否决。若普通文字页都读不对，可以让助手把实际输出与预期并排展示，核对当前安装版本和对应文档，再判断该调整用法还是换候选。若普通文字页符合要求，而扫描页被明确列为未能检索，就根据资料构成判断是否接受这一版范围。

假如助手为了让扫描页也通过，连续改写文字提取代码，却没有补上图像识别能力，就应暂停这轮修改。让它回到已查明的能力限制，解释下一次修改凭什么能解决问题。你可以接受暂时不处理扫描页，也可以让它重新调查 OCR 方案。任务要求变了，就把新的范围写清楚；不能为了保住最初的选型，把不符合需求的输出解释成成功。

三份样本只能帮助做初步判断。准备扩大使用时，还要换成真正会遇到的多页文件、文字与图像混排的页面，以及其他需要处理的情况，检查原来的结论是否仍然成立。

## 补上自己的需求，保留已有实现的积累

独立的小程序得到可接受的结果后，再让助手接入原项目。这时要说明原有文件清单仍应怎样工作，新搜索处理哪些内容，以及未能检索的页面在哪里显示。

接入时，请助手优先按库公开说明的用法调用，把自己的规则写在项目里。不要为了「统一风格」大段重写库的内部代码；那会增加需要自己验证和维护的范围。如果确实遇到库的问题，先查已有修复和版本变化，再决定更新、换库或作必要修改。

库负责的能力，通常只是完整功能的一部分。找到文字以后，还要保留它来自哪个文件、哪一页；界面需要显示片段；读取失败时需要让使用者看见；原来的文件列表也不能因为新增功能而丢失。助手要把这些部分接起来，不能只提交官方示例中的几行代码。

核对时，用同一批样本从平时使用的入口运行。除了搜索结果，还要看未能检索的资料是否仍然可见，文件位置和页码能否带你找到原文，以及关闭搜索后原有清单是否正常。如果只能证明独立小程序读出了文字，就把界面和完整流程保留为待检查项。

最后，让助手记录这次用了什么版本、为什么采用、验证了哪些材料、哪些情况仍不支持，以及怎样重新运行检查。依赖可以带有版本和适用环境要求；这些信息应进入项目的安装配置和说明，而不只留在聊天里。[PyPA 依赖规范](https://packaging.python.org/en/latest/specifications/dependency-specifiers/)

如果修改了开源项目本身，还要记录改动相对哪个版本、解决什么缺口，并保留相关检查。以后原项目更新时，让助手比较这些改动是否仍需要、是否与新版本冲突。保留原项目的更新路径，也是这次选择的一部分。

以后再次修改时，可以把这些样本交给助手重复检查。如果换了库或升级了版本，就重新核对结果，而不是沿用上一次的通过结论。

等这项工作真正完成，你应当能回答几件具体的事：搜索覆盖哪些资料，找不到时意味着什么，未读到的内容在哪里，以及下次怎样检查它仍然能用。助手负责调查已有实现、验证并补齐差异，你负责核对它是否解决了实际问题。需要长期打磨的通用能力尽量沿用成熟实现，把新代码集中在自己的需求上；这样，后续要检查和维护的工作才有明确范围。
